# Reusable widget background images

Use `ConciergeSDK.media.ensureImage({ key, prompt, aspectRatio })` for a background. The returned promise resolves to `{ url, taskId? }`. Keep the key stable for that image; an intentionally different key requests different artwork. Explicit user-driven image generation continues to use `media.createImage`.

The server scopes cached data to the authenticated user and applet, reads the existing per-user image URL, and otherwise creates one idempotent task. Its ID includes the database identity, user, applet and key. MongoDB's `_id` and BullMQ's job ID provide the concurrency boundary. Idempotent queue receipts are retained rather than removed after seven days, so recovery after a lost enqueue acknowledgement cannot resubmit paid work. Ordinary tasks retain their existing retention policy.

Before returning a new task, the server saves its ID in the image's data key. The SDK waits for the task and calls the server again to save the completed URL independently of task history. A later visit performs that same finalization if the original widget closed. Failed or missing saved tasks are not automatically replaced. Cache and persistence failures propagate to the widget's fallback; do not catch them by calling `createImage`. Expired or unavailable image URLs likewise do not authorize another generation.

The old widget-generation example incorrectly treated `data.get(key)` as `{ found, value }`, although the SDK returns the value directly. Runtime loading and direct sandbox previews now recognize that example's adjacent cache/read/generate/save sequence and replace it with `ensureImage`, using the original key and generation options. The repair parses inline JavaScript and changes only the recognized sequence. Custom code with extra side effects, dynamic generation options, or a different data contract is left unchanged. Saved source and published revisions are not rewritten, so no bulk database migration is required. Open pages must reload to receive the repair.

Validation covers cached URLs, missing caches, applet/user boundaries, failed tasks, interrupted enqueues, simultaneous requests, direct editor previews, and the saved-example repair. A local integration canary used an isolated MongoDB database and Redis queue with no image worker: 32 concurrent callers produced one task and one queued job. Lost-acknowledgement recovery reused that job. No image-provider calls were made.
