Administrators can open **Admin → Token Usage** to monitor spending and control allowances. The portal opens on **Budget control**, which loads independently of historical usage. Search by key name or fingerprint, filter for keys needing attention or unlimited access, and sort by spend or name. Keys with labels or policies appear even when they have no usage in the selected history period. The cards summarize saved spending across each key's current budget window, capped keys, keys needing attention and windows awaiting a snapshot.

Each key shows its cap, recorded spend, remaining allowance and reset time. **Near cap** means at least 80% used; **Cap reached** means recorded spend meets or exceeds the cap. **Budget blocked** means the cap is zero. The progress bar stops at 100%, while the dollar amount still shows any overshoot. A missing snapshot is **unknown**, not zero. Snapshot timestamps show when estimates were saved; idle keys can have old timestamps without an accounting outage. Policy data refreshes every 30 seconds, and spending snapshots usually follow activity by about a minute. If refresh fails, the last data remains visibly marked and editing is disabled until a successful refresh. These indicators describe budget accounting, not API gateway suspensions or live Redis health.

Choose **View activity** to investigate a key's model breakdown and interval chart/table. **By model**, **Key activity** and **Daily usage** show historical data. The 7-, 30-, and 90-day selections are elapsed periods ending when refreshed. **Today** and daily/hourly buckets use UTC. Press **Refresh** to advance the window. Aggregates can lag by up to one minute; a load error is not zero usage. **Export budgets** downloads the current filtered key list, including caps, saved spend and snapshot/reset timestamps; interval CSV export remains available in key activity.

**Total Tokens** includes uncached input, output, cache writes, and cache reads. Estimated historical costs use the currently configured model prices rather than provider invoices. `codex-auto-review` uses the configured GPT-5.6 Luna prices unless it has its own explicit price. Dated OpenAI snapshot IDs use the configured base model price when no exact snapshot price is available. If pricing or token details are missing, known costs still appear in the summary, model/key/day tables, interval charts and 30-day projections, marked **Partial**. These amounts exclude unpriced usage and can understate spending. The warning lists the affected models. **— Unpriced** means there is no calculable cost; it does not mean zero. Legacy requests with only a total token count remain unpriced, while known costs for other requests using the same model remain visible. Interval CSV exports include `cost_status` (`estimated`, `partial`, or `unavailable`), `unpriced_requests`, and `unpriced_models` so missing costs remain explicit outside the portal.

Each key has a weekly budget. The server default is **unlimited** unless your administrator configures an allowance. Its first request after budget enforcement is enabled starts the first week; subsequent seven-day windows follow that anchor automatically, even if the key is idle. No manual reset is needed. Different keys can reset at different times, so the budget summary does not represent one calendar week.

Choose **Edit weekly cap** to set a dollar amount, **Use default** to restore the server allowance, or **Unlimited** to remove the cap. Zero blocks new generation requests. **Cancel** discards unsaved edits. Changing a cap preserves the current week's spend and reset schedule. Budget spend belongs to the current budget week, independently of the history window selected above. Saving reports success separately from the approximately one-minute enforcement delay.

After saving, confirm the new cap on the key’s card. If saving fails, refresh the page and check the displayed cap before trying again; the error does not confirm that the change was saved.

Cortex checks the budget before starting public REST generation requests. At the estimated cap, new requests receive HTTP 429 with the reset time and Retry-After. Already-running requests can complete and exceed the cap. Requests explicitly rejected by the provider (such as invalid input, authentication failures, or rate limits) do not consume the weekly allowance. Interrupted responses or missing model prices use conservative fallback estimates, marked in the budget display. This is an approximate spending guard, not an exact billing limit. It does not replace separately suspended credentials or gateway blocks, and does not apply to internal GraphQL/entity work.

Allowance checks and increments use shared Redis counters. Mongo stores the policy and periodic spend snapshots. Cap edits and displayed spend can take about one minute to catch up. During accounting outages, Cortex uses the last locally known allowance and continues serving requests; additional spend may occur. Redis recovery restores the last saved snapshot, so recent unsaved or outage usage may be absent from the allowance. This availability-first behavior is intentional for approximate limits.
